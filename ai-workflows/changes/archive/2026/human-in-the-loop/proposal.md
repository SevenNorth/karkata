# 变更提案：增加 Human-in-the-Loop 用户输入协议

## 背景

Karkata 当前的 `send()` 只能连续调用模型和工具，直到完成、失败或中止。模型若缺少必要信息或需要用户确认，只能结束当前运行，再由宿主发起一个新的 `send()`；这会把同一任务拆成两个运行，也无法表达“原任务正在等待回答”。高风险操作确认、参数补充和人工判断因此缺少统一的 Runtime 契约。

page-agent 通过内置 `ask_user` 工具和 `onAskUser(question, { signal })` 回调解决基本问答。Karkata 需要保留这种模型侧工具体验，同时为 Headless 宿主提供可订阅、可响应、可取消且能隔离迟到回答的显式协议。

## 目标

- 允许显式启用 Human-in-the-Loop 后，模型通过稳定的 `ask_user` 特殊工具请求用户输入。
- 让宿主订阅当前输入请求，并通过请求 ID 回答后恢复同一次 `send()`。
- 增加 `waiting_for_input` 状态，供 UI 区分模型/工具运行与等待用户。
- 让等待复用现有运行超时、手动取消、dispose 和迟到结果隔离语义。
- 将有效回答作为原 Tool Call 对应的 Tool Result 送回模型，保持消息配对和会话原子提交。

## 范围

- Core 新增显式 Human-in-the-Loop 配置、请求类型、请求订阅、`respond()` 和等待状态。
- Core 在启用时向模型工具快照注入保留名称 `ask_user`，并验证其字符串问题输入。
- 首版回答为非空字符串；确认场景由问题文本和字符串回答表达。
- 定义无当前请求、错误 ID、重复回答、取消/超时后回答和监听器异常的行为。
- 更新 README、Runtime 设计、消息与会话协议及取消与超时协议。

## 非目标

- 不提供 React、Vue、Web Component、弹窗或表单 UI。
- 不提供 choice、多选、文件上传或任意结构化回答 Schema。
- 不提供每个请求独立的超时；等待受现有整次运行 `timeoutMs` 控制。
- 不实现工具级审批策略、权限系统或自动阻止高风险工具；模型请求确认本身不是安全边界。
- 不持久化或跨进程恢复未决请求，不允许进程刷新后继续等待。
- 不把 `ask_user` 实现为可替换、可移除或可作用域化的普通注册工具。
- 不实现上下文摘要、自动压缩或通用 Agent 事件流。

## 验收标准

- [x] 未启用 Human-in-the-Loop 时，模型工具集合和现有行为完全不变；启用后每一步包含唯一的 `ask_user` 特殊工具。
- [x] 模型调用 `ask_user` 后，Agent 发布带唯一 `id`、`runId`、`step` 和 `prompt` 的冻结请求，状态变为 `waiting_for_input`，原 `send()` 保持未决。
- [x] 当前请求订阅者在订阅时可立即得到未决请求；单个订阅者抛错不影响其他订阅者和运行。
- [x] `respond(request.id, answer)` 只接受当前请求的非空字符串回答；接受后状态恢复 `running`，回答成为匹配原 `callId` 的成功 Tool Result，模型继续同一次运行。
- [x] 错误 ID、重复回答、无未决请求及终止后的迟到回答返回 `false`，不修改消息、状态或结果；非法回答同步抛出 `TypeError`。
- [x] `abort()`、整体超时和 `dispose()` 能及时结束忽略取消的用户等待；终止后清除未决请求，迟到回答不能恢复运行。
- [x] 失败、中止或超时运行不提交包含未配对 `ask_user` Tool Call 的消息；成功运行提交完整的 Tool Call/Result 序列。
- [x] 同一 assistant 响应中的多个 `ask_user` 调用按现有 Tool Call 顺序逐个等待，同一 Agent 仍禁止并发 `send()`。
- [x] 启用 Human-in-the-Loop 时，普通工具不能注册、替换或通过 scope 注入保留名称 `ask_user`，避免重复定义和执行歧义。

## 风险

- 该变更修改公共 API、`AgentStatus`、模型工具集合和 Agent 主循环，需覆盖状态机及取消竞态。
- 用户回答进入模型上下文，宿主必须将问题和回答按不可信文本渲染；Runtime 继续使用工具结果序列化与长度限制。
- `ask_user` 依赖模型主动调用，不能保证模型在危险操作前一定请求确认，不能替代宿主侧授权策略。
- 规模评估为 8 个实施任务，影响 Core 与文档，不需要拆分独立 change；建议实现完成后作为单独 Git 提交交付。

## 待确认项

- 无。用户已确认采用 Human-in-the-Loop 方向；具体首版边界按本提案进入审批。
